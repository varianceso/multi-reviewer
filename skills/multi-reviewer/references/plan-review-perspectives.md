# 四类方案评审视角

> 上位文件:`SKILL.md`(索引);本文件展开模式 B 的四类子模式(产品/技术/测试/上线)各自的评审视角差异,以及产品方案为何不双盲。

---

## 1. 四类方案的客观基线强度

reviewer 评审一份方案,本质是"读文档 + 核查事实 + 给🟢/🟡/🔴"。四类方案的差异在于**事实基线的强度**——基线越强,reviewer 越能差异化判断,双盲交叉越有价值。

| 方案 | 客观基线 | 双盲交叉的有效性 | 本协议处理 |
|---|---|---|---|
| 技术方案 | **强**(源码 / SQL / API 现状) | 高 — 各自核查源码,易出差异化结论 | 双盲 |
| 上线方案 | 中(基础设施现状 + 历史回滚 / 监控配置) | 中 | 双盲 |
| 测试方案 | 中(已定稿的产品/技术方案 + 历史 bug 模式) | 中 | 双盲 |
| 产品方案 | **弱**(主观判断为主,LLM 摸不到用户调研/竞品/商业数据) | 低 — 两个 LLM 大概率同源偏差 | **单 reviewer**(例外) |

## 2. 为什么产品方案采单 reviewer 模式

### 2.1 同源偏差风险

产品方案里大量是**主观判断** — 用户价值、商业模式、产品节奏、需求边界。这些 LLM reviewer 通常摸不到客观数据,只能靠训练数据里的"产品常识"判断。两个 LLM reviewer 大概率会犯**同一种偏差**:

- 都偏"功能完整"(忽略 MVP 思路)
- 都低估"用户成本"(认为用户会愿意学新功能)
- 都过度乐观(覆盖度估计偏高)
- 都偏向"覆盖更多人"(忽略边缘用户)
- 都倾向"全自动化"(低估人工兜底的必要性)

如果硬上双盲,两份 review 大概率结论**高度一致** → 给主 agent / 用户错觉:"两个独立视角都通过了,方案稳"。**但其实只是一个偏差被复刻了一次,而非两个独立判断**。这种"伪交叉"比明确不交叉更危险。

### 2.2 协议层应对

1. **放弃双盲**:产品方案只派一个 reviewer 跑一次。主 agent 收到 1 份 review 即可,无对比环节,直接逐条 AskUserQuestion 跟用户裁决
2. **保留 `.{a-name}/.{b-name}` 占位符,但语义是"任一即可"**:`product-review-prompt.md` 里的 reviewer 在 Step 1 "选择归档目录" 时从所有配置的归档目录(默认 `.{a-name}/` `.{b-name}/`,N reviewer 配置时含更多)中任选一即可,**不**执行"识别 A/B/C/D 身份"的双盲动作。用户贴 prompt 给手边任一 reviewer agent 即可
3. **强制清单化**:模板里塞一份"产品方案常见盲点清单",reviewer 强制按清单逐项核查 — 把主观题转成填空题,LLM 更擅长
4. **强制假设外露**:reviewer 必须显式列出"我的判断基于以下用户场景 / 市场 / 竞品假设",假设错了主 agent / 用户立刻能看出
5. **主 agent 主动 Spike 兜底**:产品方案的 finding 主 agent 必须复核一遍假设是否成立,**不要直接转交给用户**

### 2.3 这个例外的边界

- 仅产品方案是单 reviewer 例外
- 技术 / 测试 / 上线 三类都继续双盲(各自基线足够强,差异化判断成立)
- 角色不对称(reviewer-A 扮 PM、reviewer-B 扮用户)曾被考虑,但**会破坏 `archive-and-blind.md` §5.1 的双盲对称原则**(对 A/B 给不同指令),v1.3 不采用

### 2.4 报告后的主 agent SOP(假设核查 → dismiss)

收到 B1 reviewer 报告后,主 agent **必须**按以下 4 步处理,**不允许直接逐条 AskUserQuestion 让用户裁决**(那等于把假设核查的负担全推给用户)。

| Step | 动作 | 完成判定 |
| --- | --- | --- |
| **1. 抽取假设** | 读 reviewer 报告 §2 "我的判断基于以下假设",列出每条 finding 直接依赖的假设(形成"finding ↔ 假设"对应表)。**没标假设的 finding 标记为"假设缺失"**(走 case 003 检测分支:退回 reviewer 重写) | 对应表完成,缺失项已退回 |
| **2. 假设逐条核查** | 对每条假设打三档:🟢 **可核实**(主 agent 能用现有信息或 1-2 步 spike 验证 → 假设成立)/ 🟡 **不可核实**(超主 agent 能力,需用户判断)/ 🔴 **已反例**(主 agent 已看出反例,假设站不住) | 每条假设有明确状态 |
| **3. 主 agent 出 dismiss 倡议** | 对 🔴 已反例假设对应的 finding,标"建议 dismiss(理由:假设 X 已被反例 Y 推翻)";对 🟡 不可核实的标"待用户裁决";对 🟢 假设成立的 finding 标"建议保留 / 进 case" | dismiss 倡议清单 |
| **4. AskUserQuestion 一次性收尾** | 把"建议 dismiss + 建议保留 + 待用户裁决"三组 finding **一次性呈现**给用户,让用户最终拍板:同意 dismiss 哪些 / 保留哪些 / 退给 reviewer 哪些。dismiss 倡议必须带"主 agent 反例"作为依据,**禁止只说"假设站不住"** | 用户给出明确指令,进入下一阶段 |

**反 anti-pattern**:

| Anti-pattern | 为什么不好 |
|---|---|
| 主 agent 看完报告**直接逐条**问用户 | 等于把假设核查全推给用户,B1 协议的设计意图(主 agent 兜底假设核查)落空 |
| 主 agent **自己 dismiss** 不问用户 | 最终决策权在用户 / 产品 owner;主 agent 越界 |
| 跳过报告 §2 "假设外露"段直接进 finding 列表 | 退化到 case 003 漏洞(假设外露偷懒未检测) |
| dismiss 倡议只说"假设站不住"不给反例 | 用户无法判断主 agent 的反例是否成立,等于盲签 |

**与 case 003 的关系**:case 003 修复时加了 SKILL.md §8 B1 分支 4 行 checklist(查"假设节存在"+"假设过笼统退回"+"主 agent Spike 复核"+"全 dismiss 兜底")。本节 §2.4 把那个 checklist 升级为完整 SOP — checklist 解决"防偷懒",SOP 解决"防偷懒之后怎么办"。SKILL.md §8 B1 分支应引用本节而非重复列步骤。

## 3. 四类方案的"必查维度"

每类模板里都强制 reviewer 按下述维度逐项核查,不允许"跳过"。维度数量保持 5–7 个,过多会稀释信号。

### 3.1 产品方案(单 reviewer)

reviewer 角色:**资深产品 / 业务专家 + 用户体验视角**

| 维度 | 评估关键问题 |
|---|---|
| **用户价值** | 解决什么真实痛点?方案达成了痛点吗?过度设计了吗? |
| **用户成本** | 用户为用上本能力要付出多少学习 / 操作 / 迁移 / 心智成本?方案考虑了吗? |
| **边缘用户** | 哪些用户群本方案兼顾不到?他们的退路是什么? |
| **商业边界** | 与既有产品 / 服务的边界清晰吗?有重叠 / 冲突吗?定价 / 资源分摊是否被讨论? |
| **度量回路** | 方案上线后怎么知道有效?成功 / 失败指标定义清晰吗?如何回收数据? |
| **上下游协作** | 涉及多团队 / 多角色协作时,边界与责任分明吗?谁来 own? |
| **数据 / 合规** | 涉及用户数据的部分,合规性 / 脱敏 / 留存 / 跨境策略清晰吗? |

**额外硬性要求**:reviewer 必须显式给出一段"我的判断基于以下假设" — 列出本次评审依赖的用户场景、市场状态、竞品参照、组织假设。便于主 agent / 用户审视假设是否成立。

### 3.2 技术方案(双盲)

reviewer 角色:**资深工程架构 / 系统设计专家**(同 1.2.0 既有 tech-review-prompt)

| 维度 | 评估关键问题 |
|---|---|
| **架构一致性** | 与现有架构层次 / 边界一致?新增的抽象合理? |
| **接口契约** | Req / VO 友好?字段命名一致?错误码语义清晰? |
| **SQL / 存储** | 字面对齐老 SQL?执行计划假设?索引使用?数据漂移? |
| **并发 / 时序** | 跨服务调用的时序假设?并发场景下数据一致? |
| **鉴权 / 审计** | 越权追溯?敏感数据脱敏?审计字段完整? |
| **联调 / 编译** | 跨服务 / 跨仓的契约依赖?共享代码重构影响面? |
| **工时 / 风险 / 开工** | 估算合理?风险清单覆盖度?编码前必办项完整? |

**额外硬性要求**:**代码核查 > LLM 印象** — 任何对源码 / 类名 / 方法签名 / SQL 字段的引用都要打开文件核对,不准凭印象下断言。

### 3.3 测试方案(双盲)

reviewer 角色:**资深 QA / 测试架构专家**

| 维度 | 评估关键问题 |
|---|---|
| **测试范围** | 覆盖了产品 / 技术方案的全部新能力?有无遗漏(尤其是新接口、新数据流)? |
| **用例分布** | 正常路径 / 边界 / 异常 / 性能 / 安全 各类比例合理? |
| **测试金字塔** | 单元 / 集成 / E2E 配比合理?未滥用 E2E?未把集成当单元跑? |
| **自动化策略** | 哪些自动化、哪些手工?选择依据?自动化的成本 / 维护性合理? |
| **数据准备** | 测试数据来源(造数 / 脱敏生产数据)?可重复性?敏感数据合规? |
| **环境策略** | 测试环境与生产差异?差异是否影响测试有效性?(经典坑:mock 通过、prod 翻车) |
| **回归粒度 / 度量** | 上线前回归范围?触发时机?通过 / 失败判定标准明确,无主观项? |

**额外硬性要求**:**前置依赖核查** — reviewer 在评测试方案时,必须先把"已通过评审的产品 / 技术方案"作为输入读完(主 agent 在 prompt 里给路径)。如果产品 / 技术方案还没通过评审,**直接报"前置不成立"** 而不是硬评。

### 3.4 上线方案(双盲)

reviewer 角色:**资深 SRE / DevOps / 发布管理专家**

| 维度 | 评估关键问题 |
|---|---|
| **发布策略** | 灰度顺序 / 比例 / 触发条件?为什么这样设计? |
| **回滚预案** | 触发回滚的条件清晰?回滚到哪一版?承诺多久内回滚? |
| **监控告警** | 关键指标阈值合理?告警通道有人响应?响应预期时长? |
| **数据迁移** | DDL 顺序?跟代码合入时序?可重入(幂等)吗? |
| **依赖外部** | 上下游服务通知到位?切换窗口约定?跨团队配合点? |
| **灾备演练** | 上线前演练过完整故障链路吗?盲区? |
| **操作手册 (runbook)** | 完整?上线人员熟悉每一步?有 dry-run 验证吗? |

**额外硬性要求**:**基础设施事实核查** — reviewer 必须核查基础设施现状(CI/CD pipeline、监控配置、历史故障 / 回滚案例),不要凭想象判断"上线策略合理"。如果某些基础设施信息访问不到,在报告里明确标"未核实"。

## 4. 四类的共骨架(模式 B 通用)

虽然视角不同,所有方案模板共享同一份骨架。这是"共骨架不同视角"的具体落地:

| 段 | 共享部分 | 各自不同 |
|---|---|---|
| `⚡ 立即执行` | 7 步骨架(自我识别 → 阅读 → 旧评审 → 核查 → 起草 → 落盘 → 总结) | 产品方案"自我识别"段简化(无 A/B 区分) |
| `你是谁(角色)` | 段结构通用 | **角色画像**(产品 / 工程架构 / QA / SRE) |
| `任务` | 段结构通用 | 一句话点出"评什么类型方案" |
| `评估对象` | 主文档 + 辅助参考结构 | 辅助参考的具体类型(竞品文档 / 老接口源码 / 历史 bug / 历史故障案例) |
| `回看上轮 / 前轮已知盲点` | 共享(`multi-round-regression.md`) | — |
| `评估方法(纪律)` | 通用纪律 | 各类多一条专属:**产品**=显式列出假设;**技术**=代码核查;**测试**=前置依赖核查;**上线**=基础设施事实核查 |
| `必须覆盖的评估维度` | 模板格式一致 | **维度表内容(本文 §3)** |
| `评估输出格式` | 共享 `report-format.md` 骨架 | — |
| `输出归档路径` | 共享(主仓 `.{reviewer-x}/<slug>/reviewer/<date>/`)| 产品方案在 Step 1 从所有 `.{a-name}/.{b-name}/...` 中任选一(语义"任一即可",不做双盲身份识别) |
| `双盲约束` | 通用 | 产品方案此段改成"单 reviewer 声明" |
| `硬约束` | 共享 `hard-constraints.md` 7 条 | — |

## 5. 主 agent 选模板的指引

进入 skill 后第一件事 AskUserQuestion 5 选 1(详见 `SKILL.md` §1)。用户选了之后:

| 用户选择 | 主 agent 复制的母板 | 派发逻辑 |
|---|---|---|
| 产品方案评审 | `product-review-prompt.md` | **单 reviewer**:告知用户"贴给 reviewer-A 或 reviewer-B 任一即可" |
| 技术方案评审 | `tech-review-prompt.md` | 双盲:分别贴给 A 和 B |
| 测试方案评审 | `test-plan-review-prompt.md` | 双盲:同上 |
| 上线方案评审 | `rollout-review-prompt.md` | 双盲:同上 |
| QA 回归 | `qa-regression-prompt.md` | 双盲:同上 |

**模板路径优先级**:

1. `<repo>/.claude/rules/<name>-prompt.md`(项目母板,init.mjs 已替换 reviewer 名)— 优先
2. `<skill-path>/templates/<name>-prompt.md`(skill 模板)— 项目母板缺失时回退

## 6. 与多轮回归(`multi-round-regression.md`)的关系

四类方案评审都支持多轮回归 — 同一份方案改了再评、案例沉淀纪律不变。但有一处特化:

**产品方案的 case 沉淀**:因为单 reviewer,case 沉淀只有一份 reviewer 视角(没有"两 reviewer 差异化"概念)。沉淀标准从"差异化"放宽为"假设站不住":
- reviewer 抓到的 finding,主 agent 回看 reviewer 的"假设外露"段
- 假设站不住 → 这个 finding 进 case(下轮重点验证)
- 假设站得住但用户判断"不修" → finding 不进 case(已知风险接受)

技术 / 测试 / 上线 的 case 沉淀仍按 `multi-round-regression.md` §3 标准(差异化 + 可迁移)。

## 7. 反 anti-pattern

| Anti-pattern | 为什么不好 |
|---|---|
| 产品方案硬上双盲 | 两份 review 高度一致 → 给主 agent / 用户错觉"双视角都过了",但其实是同源偏差被复刻 |
| 给产品方案 reviewer 不对称指令(A 扮 PM、B 扮用户) | 破坏 `archive-and-blind.md` §5.1 双盲对称原则;两份产出本质上是两个不同任务,无法对比 |
| 测试方案没等产品 / 技术方案通过就评 | 测试方案的"测试范围"维度评不出来 — 因为不知道要测什么 |
| 上线方案不核查基础设施现状 | reviewer 凭想象判断"灰度策略合理",但实际 CI/CD 不支持该灰度模式 |
| 四类方案塞同一份模板 + plan_type 占位 | 视角差异不显式,reviewer 不知道用哪种纪律,流于形式 |
