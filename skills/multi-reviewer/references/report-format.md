# 报告格式与严重度

> 上位文件:`SKILL.md`(索引);本文件适用 reviewer 产出的 `qa-report.md`(模式 A)与 `{方案名}-evaluation.md`(模式 B)。

## 1. 严重度分级

| 级别 | 定义 | 处置 |
|---|---|---|
| **BLOCKER** | 功能不可用 / 数据错误 / 安全漏洞 / 破坏零影响约束 | 必须在合入前修复 |
| **HIGH** | 边界 / 异常下行为不正确;方案偏差较大;覆盖明显不足 | 强烈建议修复,修不了要明确豁免理由 |
| **MEDIUM** | 小偏差 / 健壮性不足 / 轻微降级 | 建议修复,可进下一迭代 |
| **LOW** | 风格 / 命名 / 注释 / 文档小问题 | 可选修复 |
| **NOTE** | 观察 / 假设澄清 / 未验证项 / 建议补测 | 不是问题,只是留信息 |

## 1.1 finding 依据外露(强制)

**所有 finding 必须显式外露依据,否则降级到 LOW 或合并入 NOTE 区。**

为什么强制:LLM 评审天然会出"应该没问题 / 大概率稳"这种**没依据的模糊判断**(case 003)。无依据的断言主 agent 与用户都无从核验,等同噪声。

每条 finding 的"依据"字段必须落到下表四类之一(可多选,但**至少一条**):

| 依据类型 | 例 | 适用模式 |
|---|---|---|
| **源码行号** | `<file>:<line>`,如 `src/main/java/UserService.java:42-58` | B2 / A |
| **配置 / SQL / DDL 片段** | 配置文件路径 + 关键字段;SQL 语句节选 | B2 / B3 / B4 / A |
| **历史 bug ID / 故障复盘引用** | 项目 issue 编号、复盘文档锚点 | B3 / B4 |
| **命令输出 / 真实运行结果** | `curl` 输出、单测 console、CLI dump(脱敏后) | A |

模板 finding 段的"**依据**"字段是**强制**字段,不是可选项。

**B1 产品方案例外**:B1 单 reviewer 模式不外露"客观依据"(因 LLM 评产品方案缺客观基线),改为外露"**主观假设**"(用户场景假设 / 市场假设 / 组织资源假设)。详见 `plan-review-perspectives.md` §2 与 `<skill-path>/templates/product-review-prompt.md`。**不要混淆**:
- B2/B3/B4/A → 外露**客观依据**(可被主 agent 复核的事实)
- B1 → 外露**主观假设**(主 agent 无法复核,但用户能审视)

**没东西可外露怎么办**:
- 真没依据 → 不该写成 finding,写到 NOTE 区作"观察"
- 想说但暂时验不了 → 标 `[NOTE]` + 解释"暂未验证"+"建议谁验"

## 2. 模式 A 报告骨架(qa-report.md)

```markdown
# QA 回归报告 - <需求短名/分支名>

- 执行者:reviewer-A | reviewer-B(写你自己的标识,例:codex / opencode / cursor)
- 执行时间:YYYY-MM-DD HH:mm
- 工作根目录:<repo 绝对路径>
- git HEAD:
  - <primary-repo> = <short-sha>(branch: <分支名>)
  - <secondary-repo> = <short-sha>(若需求跨多仓时填,否则删除此行)
- 本次回归的 prompt:<绝对路径指向 .claude/<slug>/<YYYY-MM-DD>/qa-regression-prompt.md>

## 1. 跑过的验证

| # | 验证项 | 状态 | 耗时/记录 |
|---|---|---|---|
| 1 | 读完 N 份设计文档 | [x] | — |
| 2 | git diff 审 <key-file> 纯追加 / 改动符合方案 | [x] | +72/-0 (忽略空白) |
| 3 | 本地单测 <TestClass> | [x] | 15/15 pass |
| 4 | 鉴权自检 / 健康探针 200 | [x] | — |
| 5 | 业务接口 <endpoint> with <test-data> | [x] | 380 条返回 |
| 6 | 客户端 / CLI 端真实执行 | [ ] | **未验证**(原因:本地未启动) |

(状态图例:[x] 已通过 / [ ] 未验证 / [!] 验证发现问题)

## 2. 发现的问题(按严重度排序)

### [BLOCKER] <一句话标题>
- **定位**:`<file>:<line>` 或 `<endpoint>` 或 `<模块>`
- **现象**:实际观察到的行为,尽量复制粘贴原始输出(脱敏后)
- **期望**:对照设计文档的哪一节说明应该是什么
- **依据**(强制,详见 §1.1):源码行号 / 配置片段 / 历史 bug ID / 命令输出 至少一条
- **复现步骤**:最小化命令序列
- **建议修复方向**:不要写完整代码,给出思路

### [HIGH] <一句话标题>
...

### [MEDIUM] <一句话标题>
...

### [LOW] <一句话标题>
...

### [NOTE] <一句话标题>
...

## 3. 与技术方案的偏差(如有)

对比 `tech-design-*.md` 与实际代码的差异。区分:
- 实现漏做(代码缺方案里声明的行为)
- 方案漏写(实现比方案多做,但是合理)
- 方案/实现都不对(跟需求对齐上有问题)

## 4. 漏测 / 建议补测

列出主 agent 单测 + 本次 QA 回归都没覆盖到的场景。分级:
- **建议强补**:核心路径 / 常见异常
- **建议选补**:罕见异常 / 性能边界

## 5. 结论

- **决定**:可合并 / 建议补测后合并 / 不建议合并
- **一句话理由**:
- **给实现者的建议**:若不合并,最短可合路径是什么

## 附录(可选)

- 验证用命令的完整列表(方便复现)
- 异常日志的脱敏片段
```

## 3. 模式 B 报告骨架(evaluation.md)

```markdown
# {需求短标题}技术方案 {版本号} 评估报告

> **评估对象**:{方案文档相对路径}
> **评估时间**:{YYYY-MM-DD}
> **评估人**:[reviewer-A / reviewer-B](改为你自己的标识)
> **结论**:[🟢 通过 / 🟡 有条件通过 / 🔴 阻塞,{编码阶段} 不可启动]

## 1. 总体评价

(整体打分表,各维度 🟢/🟡/🔴 + 一句话理由)

## 2. 准确性核查

(对方案中可验证断言的核对结果,逐项 ✅/⚠️/❌,不能凭印象,要给文件路径或代码引用)

## 3. 关键变更逐项评审

(每个关键变更一节,结构:【现状/方案设计】【你的判断】【依据/反例】【建议】)

## 4. 整体维度评审

(接口契约 / SQL 性能 / 审计 / 联调 / 工时 / 风险清单 / 开工检查表)

## 5. 阻塞项(必须 {编码阶段} 前闭环)

(列出绝对不能放过的 🔴 项,理由 + 必要动作)

## 6. 建议调整清单(优先级排序)

(列出可优化的 🟡 项,按"必改 / 强烈建议 / 锦上添花"分级)

## 7. 与上一轮评审的回应度对照

(回看自己上一轮报告中提出的问题,逐项对照当前版本是否回应、回应是否充分。首次评审则写"无,首次评审")

## 8. 评审结论

(综合判断 + 是否同意进入 {编码阶段})

## 附录 A:代码核查证据

(任何在正文里引用的代码/文件路径/行号/SQL 片段,在这里附原文片段或截取证明)
```

## 4. 控制台摘要行

报告写完后,在控制台**只**输出一行摘要(不要把报告正文打印出来):

```
QA report saved: <path1> ; <path2>   (BLOCKER=x HIGH=y MEDIUM=z LOW=w NOTE=n)
```

示例(单仓):

```
QA report saved: <primary-repo>\.{reviewer-a}\<slug>\reviewer\<YYYY-MM-DD>\qa-report.md   (BLOCKER=0 HIGH=1 MEDIUM=2 LOW=3 NOTE=5)
```

模式 B 的摘要把 `QA report` 换成 `Evaluation`:

```
Evaluation saved: <primary-repo>\.{reviewer-a}\<slug>\reviewer\<YYYY-MM-DD>\{方案名}-{版本}-evaluation.md   (Blockers=1 Strong=2 Optional=3)
```

## 5. 未验证项的写法

不要静默跳过任何验证维度。如果某项因环境 / 权限 / 依赖缺失跑不了,在"跑过的验证"表里填 `[ ]` 并在"耗时/记录"列说明原因,必要时在 NOTE 区展开。

**反例**(错误写法):直接不写这一行
**正例**(正确写法):

```markdown
| 6 | 客户端真实 execute | [ ] | 未验证:本地依赖缺失,PATH 里也没可执行入口 |
```

并在 NOTE 区:

```markdown
### [NOTE] 客户端真实 execute 未跑通
- 原因:本地 node_modules 缺失;`npm install` 拉超时
- 影响:模式 A 第 6 项验证缺位,主 agent 已自验,需用户决定是否需要 reviewer 补跑
- 建议:可在测试环境直接 npm i 后复跑;或主 agent 提供 docker 镜像
```

## 6. 报告写完前的最后一遍检查

- [ ] 所有 finding 都有"定位 / 现象 / 期望"三段
- [ ] **所有 finding 都有"依据"字段**(参 §1.1;B2/B3/B4/A 写客观依据,B1 写主观假设)
- [ ] 没"依据"或依据写不出来的 finding 已降级到 LOW / 合并到 NOTE 区
- [ ] 所有 token / 真实姓名 / 工号 已脱敏(参 `hard-constraints.md` §5)
- [ ] "跑过的验证"表里没有静默跳过的行
- [ ] 控制台摘要行格式正确
- [ ] 写到了正确的归档路径(`.{your-agent}/<slug>/reviewer/<date>/` 而不是 `.claude/`)
