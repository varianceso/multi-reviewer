# 三方协同完整流程

> 上位文件:`SKILL.md`(索引);本文件是三方协同的完整版,展开模式 A/B 流程图、双盲三种特化、跳过条件、Spike 兜底。

## 1. 角色与职责

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **主 agent**(触发 skill 的 agent;可以是 claude / cursor / cline / codex / opencode 等任一) | 需求澄清 → 方案设计 → **编码独占** → 单测 → 自测 → 本地集成测试 → 写交叉验证提示词 → N+1 份报告对比裁决 | 不做最终 QA 回归(避免自己验自己) |
| **reviewer-A / B / C / ...**(默认 2,可配置 1-N≤26;例:codex / opencode / cursor / cline)| 评审专家:产品方案 / 技术方案 / 测试方案 / 上线方案 的独立评估;测试专家:编码后的 QA 回归 | **不改源码、不跑构建、不 commit、不清环境、不看其他 reviewer 产出**(N 路双盲) |
| **用户** | 提需求 / 审方案 / 审 PR / N+1 方结论分歧时仲裁 | — |

> **主 agent 怎么定**:用户在哪个 agent session 里触发本 skill,那个就是主 agent;一次需求只有一个主 agent 贯穿始终。
>
> **编码独占铁律**:**写代码 / 改源码 / 跑构建 / 提交 git 写操作 = 主 agent 独占**。reviewer 一律只读不写。这个分工是为了避免多 agent 同时编码冲突。
>
> reviewer-A / reviewer-B / ... 是占位符,代表"独立的 AI 工具"。常见组合:codex + opencode(默认 2 reviewer);加 cursor + cline(N=4);claude opus + claude sonnet 不同 session(此时虽然底模相同但工具链 + session 上下文不同,也能产生独立性)。
>
> **B1 产品方案永远 1 reviewer**:即使配了 N>1,B1 也只用 1 个(LLM 评产品主观题易同源偏差,详见 `plan-review-perspectives.md` §2)。

## 2. 两种模式 + 模式 B 的四类子模式

主 agent 进入 skill 后**前两件事(v1.6)**:**第 0 件事 = AskUserQuestion 拿需求 slug**(列出 `.claude/` 下现有 slug + 新建 + `_oneoff_`),拿到 slug 后立即 Read `<primary-repo>/.claude/<slug>/summary.md`(若存在)拾跨会话决策史;**第 1 件事 = AskUserQuestion 5 选 1 扁平**(产品方案评审 / 技术方案评审 / 测试方案评审 / 上线方案评审 / QA 回归)。详见 `SKILL.md` §1 + §2。

| 顶层模式 | 子模式 | 触发时机 | 主 agent 产出 | reviewer 产出 | 双盲? |
|---|---|---|---|---|---|
| **模式 A:回归**(编码后) | — | 实现完成、单测通过、本地冒烟 OK | `qa-regression-prompt.md` | `qa-report.md`(跑接口 / curl / CLI 验实现) | ✅ |
| **模式 B:方案评审**(编码前) | **B1 产品方案** | PRD 定稿,准备进技术设计 | `product-review-prompt.md` | `{方案名}-{版本}-evaluation.md`(对照"产品盲点清单" + 假设外露) | ❌ **单 reviewer 例外** |
| | **B2 技术方案** | 技术方案定稿,准备进编码 | `tech-review-prompt.md` | 同上(代码核查 > 印象) | ✅ |
| | **B3 测试方案** | 测试方案定稿,准备进测试执行 | `test-plan-review-prompt.md` | 同上(前置=已通过的产品/技术方案) | ✅ |
| | **B4 上线方案** | 上线方案定稿,准备进发布窗口 | `rollout-review-prompt.md` | 同上(基础设施事实核查) | ✅ |

**子模式独立选择**:产品 / 技术 / 测试 / 上线 任一独立可走;通常按顺序(B1→B2→B3→B4),前一份没通过评审就评下一份等于空中楼阁(测试方案尤其)。

**A 与 B 独立**:
- 重大需求(0→1 / 跨多仓 / 新 SQL):走完 B1-B4 → 编码 → A
- 中等需求(已有接口扩展):只做 A 或只做 B2 + A
- 高风险方案(数据库迁移 / 鉴权改造):必走 B2,可加 B4

> 全流程 B → 编码 → A 不在协议里强制串联,用户**分次调 skill** 即可(每次 5 选 1)。

> **为什么产品方案是单 reviewer 例外**:LLM 评产品方案时缺客观基线(用户调研 / 市场数据 / 竞品),两个 LLM reviewer 大概率犯同一种偏差("功能完整偏好""用户成本低估""过度乐观"),双盲会复刻同一个偏差,给"双视角都过了"的伪交叉错觉。详见 `plan-review-perspectives.md` §2。

## 5. 双盲原则(强制)

**通用规则**(模式 A 与 B 都适用):**N 个 reviewer 互不参考其他人的过程与产出**。把任一对方结论提前喂另一个,会让其停在"照着清单复跑",失去交叉价值。N=3 / 4 时双盲对称要求更严:不能让 A 看 B 的、也不能让 A 看 C 的、也不能让 B 看 C 的。

**模式 A 特化**:
- 提示词里**不写**主 agent 的判断性自测结论(例:"已验证通过的 5 个接口"、"发现的 3 个瑕疵")
- 让 reviewer 从零判断设计意图 → 评估实现 → 跑真实验证
- **例外**:事实性信息(可用测试角色名、数据规模、已批准的接口)可以写进提示词的"环境信息"段;判断性结论不要写

**模式 B 特化(B2/B3/B4 双盲)**:
- **允许**让 reviewer 回看**自己**上一轮的同类报告(评估方案是否回应了上一轮问题)
- **严禁**让一方看另一方的同期或历史报告
- 不要在提示词里写主 agent 对方案的"自我点评";让 reviewer 从零判断每项变更的合理性

**B1 产品方案例外(不双盲)**:
- 协议层放弃双盲 — 只一份 reviewer 跑一次。原因:LLM 评产品方案时缺客观基线,两个 reviewer 大概率犯同一种偏差,双盲会复刻同源偏差给"伪交叉"错觉
- prompt 中**保留** `.{a-name}` `.{b-name}` 占位符(及 N reviewer 配置时的 `.{c-name}` 等),但**语义是"任一即可"** — reviewer 在模板 Step 1 从所有配置的归档目录中任选一,默认按主 agent 派发指示。**不要求 reviewer 执行"识别 A/B/C/D 身份"的双盲动作**(那是 B2/B3/B4/A 的纪律)
- 模板强制 reviewer **显式列出"我的判断基于以下假设"**(假设外露)+ 强制按"产品盲点清单"逐项核查
- 主 agent 收到 1 份 review 后**自己 Spike 复核假设**,而不是直接转交给用户

## 6. 三份产出交叉对比

### 模式 A(回归报告对比,N≥2)

**共识阈值:严格多数(> N/2)**(同模式 B 的 §6 阈值表;偶数 N 正好半数 = 平局,不算共识)。

| 情形 | 判定 |
|---|---|
| **严格多数 reviewer 都报同一问题** | **必改**(独立视角中严格多数都抓到了) |
| 不到严格多数 reviewer 报(包括偶数 N 半数 = 平局)| 主 agent 做"真漏 vs 误判"甄别:读两个报告的定位 / 复现步骤,必要时实测 |
| 全员都没报某个维度 | 该维度大概率稳,但**注意"都没测到"** vs "都测了没问题"的区别(看他们的"跑过的验证"清单) |
| 多 reviewer 结论严重矛盾 | 通常是其中跑错了环境 / 角色,由主 agent 复核裁决 |

### 模式 B(方案评审报告对比)

#### B2 / B3 / B4(双盲场景,N≥2)

**共识阈值:严格多数(> N/2)**。

- N=2 时 = 2/2 都标(N/2=1,严格多数 > 1 = 2)
- N=3 时 ≥ 2/3(N/2=1.5,严格多数 ≥ 2)
- N=4 时 ≥ 3/4(N/2=2,严格多数 ≥ 3;**正好 2/4 半数算平局,不算共识**)
- N=5 时 ≥ 3/5

| 情形 | 判定 |
|---|---|
| **严格多数 reviewer 都标某项 🔴 阻塞** | **必改方案**(N 个独立视角中严格多数判定阻塞) |
| 不到严格多数 reviewer 标 🔴(包括偶数 N 正好半数 = 平局)| 主 agent 复核每份依据:事实错位 / 经验差异 / 解读分歧?必要时跟用户共识 |
| 严格多数 reviewer 标 🟡 建议 | **取并集**,按重要度排(必改 / 强烈建议 / 锦上添花) |
| 全员 🟢 通过 | 方案大概率成立;但若全员都没覆盖某维度(如未验证 SQL 性能),主 agent 单独补 Spike |
| 多个 reviewer 对同一项打分相反 | 通常其中之一误读方案,由主 agent 复核裁决;若用户能介入则用户裁决 |
| N=3+ 时结论高度分散(每个 reviewer 给不同结论) | 协议本身没设计好的信号;主 agent 应当主动 Spike + 与用户共识 |
| **关注**:全员都未提某新增能力的盲点(并发安全、跨服务时序) | 主 agent 主动 Spike 兜底,不能因"评审都没说"就默认安全 |

#### B1 产品方案(单 reviewer 场景)

只有 1 份产出 → **无对比环节**,但有"假设核查环节":

| 情形 | 判定 |
|---|---|
| reviewer 标 🔴 阻塞 + 假设站得住 | **必改方案**;主 agent AskUserQuestion 跟用户共识 |
| reviewer 标 🔴 阻塞 + 假设不成立(用户场景错位 / 竞品参照过时) | 该 finding **不上交用户**,主 agent 在裁决记录里写"假设不成立故 dismiss" |
| reviewer 标 🟡 建议 | 取全集,但主 agent 必须复核每条假设;假设成立的才给用户裁决 |
| reviewer 🟢 通过 | **不能默认稳** — 单视角通过比双盲通过更弱;主 agent 必须 Spike 1-2 个高风险维度补强 |
| reviewer 没覆盖到 §3.1(`plan-review-perspectives.md`)某维度 | 主 agent 必须自己评一遍那个维度,不能跳 |
| **全部 finding 假设都不成立**(reviewer 看错场景 / 假设全错位) | 等价为单视角"无 finding 通过";按 🟢 通过行处理 + **必走主 agent Spike 1-2 个高风险维度补强**;考虑换一个 reviewer 重跑(本次评审产出虽为零,但流程不能视为"通过") |
| reviewer 报告 **缺 §2 "我的判断基于以下假设" 段** 或假设过于笼统 | 把报告**退回 reviewer** 要求补假设,不直接进 §3 finding 裁决(详见 SKILL.md §8 B1 闭环检测 checklist) |

## 6.5 主 agent 核验报告纪律(收到 N 份报告后、走 §7 之前必做)

**v1.4 引入,v1.6 升级到 6 步。** 主 agent 收到 N 个 reviewer 的报告后,**不允许直接照 reviewer 的结论进 §6 / §7 批量裁决**。必须先完成以下 6 步纪律:

> **核心断言(v1.6 新增)**:**副 agent 严格多数共识 ≠ 主 agent 自动采纳**。哪怕 N=3 时所有 3 个 reviewer 都标某 finding 阻塞,主 agent **仍必须**亲自打开对应代码段独立判断 — 因为主 agent 在与用户交互过程中积累的上下文(用户业务理解 / 历史决策 / 未明示约束 / 跨需求依赖)是 N reviewer 看不到的;直接信副 agent 等于丢了用户主权,可能采纳"看似多数共识但实际错位"的 finding。

> **Step 1 vs Step 2 顺序(v1.6.1 澄清)**:Step 1(逐 finding 自查)与 Step 2(自扫独立判断)**职责正交,可并行**。Step 1 是**反应式** — 对副 agent 报的每条 finding 一一回应;Step 2 是**主动式** — 主 agent 自己 spike 关键路径找 N reviewer 都漏的盲点。表行序号 1→6 是逻辑分层,不是必须严格线性执行;两者结果在 Step 3 三方对照时合并。LLM 不应解读为"先 Step 1 全部读完再开 Step 2",这会拖慢 N=3+ 时的核验节奏。

> **reviewer finding 缺 file:line 时的兜底(v1.6.1 新增)**:本协议要求 reviewer 每条 finding 必带 `report-format.md` §1.1 的 4 类客观依据(源码行号 / 配置 / 命令输出 / 历史 bug ID)。**若副 agent 仍交付了缺 file:line 的描述性 finding**,主 agent **不应**放过 Step 1 自查,而应**先把该 finding 退回 reviewer 要求补依据**,再进入自查;若 reviewer 拒绝补 / 不可达,主 agent 把该 finding 标 "🟡 未核实(reviewer 缺依据)" 并独立 spike,**不要**默默 dismiss 也不要按主 agent 印象采纳。

| Step | 动作 | 完成判定 |
| --- | --- | --- |
| **1. 逐 finding 自查代码(强制,v1.6 新增)** | 对副 agent 报的**每条** finding,主 agent 必须**亲自打开 finding 指向的代码文件**(Read 实际行号 ± 上下文 5-15 行),独立判断:同意 / 不同意 / 上下文不够。**不允许仅凭"副 agent 严格多数共识"跳过自查直接采纳**。读到的关键 1-3 行片段记下来 — Step 4 AskUserQuestion 必须用 | 每条 finding 都有主 agent 自查证据(file:line + 1-3 行片段 + 独立判断),无"未读直接信副 agent"的 finding |
| **2. 自扫代码独立判断**(原 Step 1) | 除了响应副 agent finding 之外,主 agent 自己 spike 关键路径(grep 关键代码 / 读上下文 / 跑必要快速命令),形成**主 agent 自己的初判清单**(覆盖副 agent 可能漏的盲点) | 心里有自判清单(可能与 reviewer 一致 / 不一致 / 互补) |
| **3. 三方对照而非二选一**(原 Step 2) | 把"主 agent 自判 + reviewer-A + reviewer-B"(N≥3 时含 C/D/...)逐条比对;**不一致**也是有效信号 — 主 agent 漏 / reviewer 漏 / 双方对同一现象做不同诠释 都要分清 | 形成 finding 状态四象限:🟢 N+1 共识 / 🟡 部分一致 / 🔴 主 agent 自判但 reviewer 没抓到 / ⚪ reviewer 抓到但主 agent 自检漏 |
| **4. 拿不准必 AskUserQuestion(4 要素)**(原 Step 3,v1.6 加 4 要素) | 任何不能凭代码事实独立判断的 finding(设计意图歧义 / 业务约束模糊 / ROI 不清 / 用户场景未明示),立即 AskUserQuestion 交互式确认。**AskUserQuestion 选项必带 4 要素**:① 副 agent 言论(原文 / 概括 + 哪个 reviewer)② 主 agent 自查(Step 1 的 file:line + 1-3 行片段 + 独立判断)③ 具体例子(类似 git history / 现有代码对照 / 测试场景)④ 选项(同意改 / 不改 / 推延 / 其它)。**没有 4 要素的 AskUserQuestion 等于让用户在信息真空里拍板** | 不存在"待定 / 不清楚 / 我倾向于 ..." 这类悬置状态的 finding;每条交用户裁决的 finding 都带 4 要素 |
| **5. 本轮闭环优先**(原 Step 4) | 本轮发现的问题,**本轮就修** — 不挂账。除非用户在 Step 4 明确说"推延" + 给理由,否则一律本轮修复并跑短验证 | 修复在本轮 commit 中落地;无"留 v1.X+1" / "下次再说" 的脱身借口 |
| **6. ROI 低 finding 不能默 dismiss**(原 Step 5) | 即使主 agent 判断 ROI 低,也**不能自己 dismiss** — 必须列出**详细建议 + 不修的具体理由 + 修的预估成本**,让用户裁决是否真不修 | 用户对每条 ROI 低 finding 都明确表态(修 / 不修 / 推延);裁决记录在 commit message 或 changelog |

**反 anti-pattern**:

| Anti-pattern | 为什么不好 |
|---|---|
| **副 agent 严格多数共识 → 主 agent 跳过 Step 1 自查直接采纳**(v1.6 新增,**最严重**) | 副 agent 是 LLM,可能集体犯同源偏差(都误读上下文 / 都缺业务背景);N=3 时 2 票或 3 票同认 ≠ 真理;主 agent 在用户交互中积累的上下文是关键裁决依据,跳过自查 = 丢掉这部分上下文 |
| AskUserQuestion 选项**只写副 agent 言论,不带主 agent 自查证据**(v1.6 新增) | 用户从主 agent 处获得的信息密度,决定裁决质量;只甩副 agent 一句话给用户 = 让用户在信息真空里拍板,容易拍错 |
| 主 agent 直接照 N reviewer 报告做 §6 N+1 对比裁决 | 跳过自扫 → reviewer 的同源 LLM 偏差(N reviewer 都漏的盲点)无人识破 |
| 主 agent 自判与 reviewer 不一致时,**默认采信 reviewer** | reviewer 看不到 prompt 之外的全部上下文,主 agent 自判可能更准;不一致是信号不是结论 |
| 拿不准就标"留下轮验证 / 后续 follow up" | 把问题挂账,违反"本轮闭环"原则;下轮多半再次悬置 |
| ROI 低就直接说"不重要,不修",不告诉用户 | 主 agent 越权;ROI 评估、修与不修都属用户决策权 |
| "三方都没标 → 默认稳" | 同源盲点案例:所有 reviewer 用同样的 LLM 偏差判断,可能集体漏 — 主 agent 自扫覆盖关键路径才是兜底 |
| 主 agent 自扫后只汇报"已自扫,无新 finding" | 自扫过程要呈现 — 至少 1-2 句"扫了 X / Y 文件,关注 Z 维度,无新发现",让用户知道范围 |

**与 §8 Spike 兜底的关系**:

- §8 Spike = "找 N+1 都漏的盲点"(主动进攻型,Spike 维度是 LLM 偏差易漏的)
- §6.5 = "自扫 + 三方对照"(系统检测型,所有 reviewer finding 都要交叉)
- 关系:§6.5 Step 1 自扫过程中如果觉得"这块 reviewer 都没碰但我心里担心" → 立即跳到 §8 做 Spike;Spike 结果合并进 §6.5 Step 2 三方对照

**与 §7 AskUserQuestion 逐条裁决的关系**:

- §6.5 是"核验阶段"(主 agent 单方面准备好可以进用户裁决的 finding 清单)
- §7 是"裁决阶段"(主 agent 把准备好的清单逐条交用户拍板)
- §6.5 Step 3 的"AskUserQuestion 拿不准" 是 §7 的提前调用 — 拿不准的 finding 必须先问清楚才能进 §7 列表

## 7. AskUserQuestion 逐条裁决(v1.6 升级:4 要素强制)

收到 reviewer 报告后,**不要批量打包**地说"以上 5 条建议,我都修了"。每条 finding 都用 `AskUserQuestion`(或等价交互)单独拿给用户,**且选项必带 4 要素上下文**:

```
finding 编号 / 严重度 / 一句话标题
↓
context 段(4 要素,v1.6 强制 — 否则用户在信息真空里拍板):

  ① 副 agent 言论:
     [reviewer-A:line N 引用; reviewer-B:同认 / 异议 / 未提]
     [一句话概括副 agent 的判断主张]

  ② 主 agent 自查(§6.5 Step 1 产物):
     - 读了哪个文件:`path/to/file.ext:42-58`
     - 关键 1-3 行片段(贴出来):
       ```
       function X(ctx) {
         if (ctx.foo == null) return null;  // 此处副 agent 标的问题
       ```
     - 主 agent 独立判断:同意 reviewer / 不同意(理由) / 上下文不够要问用户

  ③ 具体例子:
     [类似情形 / 历史 git commit / 现有代码对照 / 测试场景模拟]
     例如:"git history c3f2a1 是同样模式,当时按 reviewer 的建议改后导致回归 bug,后回滚"

↓
选项:
  - 同意 reviewer 修改(立即修)
  - 不改(主 agent 自查理由 OK,本次不动)
  - 推延(进 backlog,本次记录但不修)
  - 其它(用户自定义)
```

理由:
1. **批量裁决会让用户失去对每条 finding 的独立判断**,模糊掉真正必改与可延后的边界
2. **(v1.6 新增)上下文不到位的 AskUserQuestion 会让用户拍错** — 用户从主 agent 处获得的信息密度决定裁决质量;只甩副 agent 一句话 → 用户没有判断依据 → 默认拍"修"或"不修"都可能错。4 要素上下文把决策依据完整呈现,让用户基于事实裁决。

参考记忆 `feedback_qa_verdict_confirm`;v1.6 4 要素来源 = v1.5 实战中"3 reviewer 同认 → 主 agent 直接信"的反例。

## 8. Spike 兜底(三方都漏掉的盲点)

当方案涉及新增能力,且 reviewer-A / reviewer-B 评审都未覆盖某关键维度时,主 agent 必须主动开 Spike:

| 盲点维度 | Spike 动作 |
|---|---|
| 并发安全 | 写 1-2 个并发场景测试,证明数据一致 |
| 跨服务时序 | 画时序图 + 模拟"上游慢响应"场景 |
| 数据漂移 | 拉测试库真实数据,对比新旧逻辑输出 |
| 性能 | 用真实数据规模跑一次,记录 P99 |

Spike 产出落 `.claude/<slug>/<date>/spike-{topic}.md`,作为后续合入决策的补强证据。

## 9. 跳过条件

下列情形可以跳过整套交叉验证:

- 一行 typo / 注释 / README 文字调整
- 纯重命名 / 纯移动重构(编译通过即可)
- 实验性 / 临时脚本类一次性产出
- 已有功能纯字段补充(无语义变化)
- 用户明确说"不用 QA / 直接编码"

涉及业务逻辑、接口契约、数据权限、鉴权链路、新数据源 / 新 SQL 设计、0→1 新能力、跨多仓改动的需求都**不在豁免范围**。
